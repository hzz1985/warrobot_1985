# معماری ایجنت‌های محلی برای ربات بورسی

**نقش دیپ‌سیک:** معمار و ناظر (طراحی، کد اولیه، تصمیم‌های نادر، بازبینی کیفیت)
**هدف:** اجرای روزمرهٔ ربات بدون فراخوانی مدل ابری؛ فقط موارد نادر به دیپ‌سیک برسد.

---

## ۰) واقعیت سخت‌افزار این سرور (اندازه‌گیری‌شده)

```
CPU      : 4 vCPU (QEMU)
RAM      : ۸ گیگابایت کل · ~۲.۸ گیگابایت آزاد
GPU      : ندارد (Microsoft Basic Display Adapter)
دیسک آزاد: ۸.۸ گیگابایت
```

**نتیجه:** اجرای یک مدل ۷B روی این ماشین در ساعات بازار ممکن نیست:

```
۷B Q4  → ~۴.۵ گیگابایت RAM (سرور آزاد ندارد) + ~۴ گیگابایت دیسک
۳B Q4  → ~۲ گیگابایت RAM (مرز خطر؛ با Chrome ربات تداخل می‌کند)
۱.۵B Q4→ ~۱ گیگابایت RAM (قابل اجرا، فقط خارج از ساعات بازار)
۰.۵B Q4→ ~۰.۴ گیگابایت RAM (قابل اجرا، کیفیت پایین برای استدلال)
```

پس معماری باید «مدل‌محور» نباشد، بلکه **قانون‌محور با قلاب مدل** باشد:
کارهای تکراری = کد قطعی (بدون LLM)، و LLM فقط برای خلاصه‌سازی/تشخیص الگو.

## ۱) لایه‌بندی

```
┌──────────────────────────── Agent Supervisor (این ماشین) ────────────────────────────┐
│  router.py     : تعیین می‌کند کار به «قانون» برسد یا «مدل» یا «دیپ‌سیک»               │
│  cache.py      : کش پاسخ‌ها (SQLite) — پرسش تکراری، صفر توکن                          │
│  batch.py      : بسته‌بندی چند سؤال در یک فراخوانی                                   │
│  summarizer.py : خلاصه‌سازی محلی قبل از ارسال به دیپ‌سیک                              │
│  ollama_client : HTTP به Ollama (اختیاری؛ اگر نبود → degraded mode)                  │
└───────────────┬─────────────────────┬──────────────────────┬─────────────────────────┘
                │                     │                      │
        ┌───────▼──────┐      ┌───────▼───────┐      ┌───────▼────────┐
        │ Agent: Login │      │ Agent: WebApp │      │ Agent: PreOpen │
        │ (قانون‌محور)  │      │ (قانون‌محور)   │      │ (قانون‌محور)    │
        └──────────────┘      └───────────────┘      └────────────────┘
                │                     │                      │
        ┌───────▼─────────────────────▼──────────────────────▼────────┐
        │        هستهٔ قطعی ربات: scheduler / flow / pnl / journal      │
        └──────────────────────────────────────────────────────────────┘
```

### اصل طراحی
```
هر «ایجنت» = یک اسکریپت پایتون با:
  ۱) تشخیص وضعیت (checks)
  ۲) اقدام خودکار مجاز (actions) با محدودهٔ مشخص
  ۳) گزارش ساخت‌یافته (JSON) + ثبت در state/agents/<name>.jsonl
  ۴) درخواست کمک از LLM فقط اگر قانون نتوانست تصمیم بگیرد
```

## ۲) فهرست ایجنت‌ها (بر اساس دردهای واقعی)

| ایجنت | مسئله‌ای که می‌بندد | نوع تصمیم | مدل لازم؟ |
|---|---|---|---|
| **A1 login-watch** | ورود نشدن در ساعات بازار (باگ کپچا/سشن) | قانون | خیر |
| **A2 preopen-order** | خطای سفارش‌گذاری پیش‌گشایش | قانون + تست | خیر |
| **A3 webapp-keeper** | کهنه‌ماندن وب‌اپ و خطای P&L | قانون | خیر |
| **A4 log-triage** | دسته‌بندی و خلاصهٔ خطاهای روز | قانون + LLM کوچک | ۱.۵B کافی |
| **A5 report-writer** | نوشتن گزارش روزانه/هفتگی | LLM کوچک | ۱.۵B |
| **A6 data-integrity** | تطبیق P&L با کارگزار | قانون | خیر |
| **A7 docs-updater** | به‌روزرسانی RUNBOOK از تغییرات | LLM متوسط | ۳B+ (خارج ساعت بازار) |
| **A8 edge-case-escalator** | بسته‌بندی موارد نادر برای دیپ‌سیک | خلاصه‌سازی | LLM کوچک + دیپ‌سیک |

## ۳) مسیریابی، کش، بچ، خلاصه

```
router.classify(task) →
   rule      : ۹۵٪ کارها (چک‌ها، سفارش، رفرش، ایمیل) — صفر توکن
   small_llm : خلاصه، دسته‌بندی، نوشتن متن — توکن صفر (محلی)
   deepseek  : فقط اگر (a) تصمیم جدید معماری (b) خطای ناشناختهٔ تکرارشونده
               (c) تغییر استراتژی — و همیشه با «خلاصهٔ آماده» و «بستهٔ سؤال»
```

```
cache : کلید = هش(نوع کار + ورودی نرمال‌شده)؛ TTL پیش‌فرض ۷ روز
batch : حداکثر ۲۰ سؤال کوچک در یک فراخوانی؛ خروجی JSON آرایه‌ای
summarize : قبل از هر ارسال به دیپ‌سیک، حداکثر ۸۰۰ توکن خلاصه
```

## ۴) حالت کاهش‌یافته (Degraded Mode)

```
اگر Ollama در دسترس نبود:
  ├─ ایجنت‌های قانون‌محور: بدون تغییر کار می‌کنند (A1,A2,A3,A6)
  ├─ A4/A5: متن قالبی از پیش تعریف‌شده (بدون LLM)
  └─ A8: صف escalation پر می‌شود؛ ارسال به دیپ‌سیک فقط با خلاصهٔ ساخت‌یافته
```

```
اگر دیپ‌سیک در دسترس نبود:
  └─ صف escalation روی دیسک می‌ماند؛ هیچ وظیفهٔ بازار متوقف نمی‌شود
```

---

## ۵) برآورد کاهش مصرف توکن

| اقدام | اثر |
|---|---|
| A1/A2/A3 قانون‌محور (بدون LLM) | حذف تقریباً همهٔ فراخوانی‌های عیب‌یابی روزانه (بیشترین سهم) |
| کش پاسخ‌ها | حذف تکرارها؛ در عمل ۴۰–۶۰٪ درخواست‌ها تکراری‌اند |
| خلاصه‌سازی محلی | ورودی دیپ‌سیک از چند هزار توکن به ~۸۰۰ توکن |
| بچ کردن | کاهش تعداد فراخوانی‌ها تا ۱۰ برابر |
| قالب‌های آمادهٔ گزارش | حذف تولید متن توسط مدل ابری |

## ۶) تصمیم‌های لازم قبل از پیاده‌سازی

1. **محل اجرای مدل محلی:** این سرور (فقط ۰.۵B–۱.۵B، خارج از ساعت بازار) یا سرور دوم خارج از ایران؟
2. **سطح اختیار ایجنت‌ها:** فقط پیشنهاد پچ، یا اعمال خودکار با تست و rollback؟
3. **اولویت اول:** ورود/پیش‌گشایش یا وب‌اپ؟

### اندازه‌گیری کیفیت مدل محلی
```
qwen2.5:1.5b  → پرسش فارسی را نفهمید (پاسخ انگلیسی و بی‌ربط)
gemma2:2b     → بدتر؛ سؤال را به «معنای زندگی» تفسیر کرد
زمان پاسخ     → ۱۵ تا ۴۷ ثانیه برای چند ده توکن (CPU تنها)
```
**نتیجه:** استدلال فارسی و تصمیم‌گیری با این سخت‌افزار ممکن نیست.
معماری به «قانون‌محور» تغییر کرد؛ مدل محلی فقط برای خلاصه‌سازی انگلیسیِ
خارج از ساعت بازار و با کش استفاده می‌شود.

### ایجنت‌های ساخته‌شده
```
agents/login_watch.py    A1 — ورود/سشن: پاکسازی پروفایل، ۳ تلاش ورود، گزارش
agents/preopen_watch.py  A2 — پیش‌گشایش: بررسی rehearsal/preready/سفارش،
                              اجرای دوبارهٔ مرحلهٔ گم‌شده، سپس escalation
agents/webapp_watch.py   A3 — وب‌اپ: HTTP 200، تازگی pnl/prices،
                              تطبیق price/avg−1 با pnl_pct، تازه‌سازی خودکار
agents/supervisor.py     اجرا + گزارش JSON + صف escalation + ایمیل روزانه
agents/llm.py            کلاینت Ollama با کش SQLite و قفل ساعت بازار
```

# API ثبت سفارش کارگزار — کشف دور ۲

## نقطهٔ پایانی
```
POST https://api.meibours.ir/Web/V1/Order/Post
Content-Type: application/json
credentials: include (کوکی نشست)
```

## بدنهٔ درخواست (ضبط‌شده از کلیک واقعی روی «خرید»)
```json
{
  "IsSymbolCautionAgreement": false,
  "CautionAgreementSelected": false,
  "IsSymbolSepahAgreement": false,
  "SepahAgreementSelected": false,
  "orderCount": 10000,
  "orderPrice": 1919,
  "FinancialProviderId": 1,
  "minimumQuantity": 0,
  "maxShow": 0,
  "orderId": 0,
  "isin": "IRO1ABAD0001",
  "orderSide": 65,
  "orderValidity": 74,
  "orderValiditydate": null,
  "shortSellIsEnabled": false,
  "shortSellIncentivePercent": 0
}
```

## پاسخ سرور
```json
{"Data":{"OrderId":0},"MessageDesc":null,"IsSuccessfull":true,"MessageCode":null,"Version":0}
```

## تفسیر
- درخواست واقعاً ارسال می‌شود و سرور `IsSuccessfull: true` برمی‌گرداند
- ولی `OrderId: 0` و فهرست سفارشات باز خالی می‌ماند → سفارش ثبت نهایی نمی‌شود
- یعنی یا payload ناقص است، یا کارگزار بعد از پاسخ اولیه آن را رد می‌کند

## قدم بعدی
1. مقایسهٔ payload با یک سفارش موفق قبلی (دو روز پیش) — همان مسیر CDP
2. بررسی فیلدهای احتمالی جاافتاده: `orderType`، `clientOrderId`، `accountType`، `validityDate`
3. پایش پاسخ `OrderStateV3` (کانال `orderstatev6`) برای دیدن پیام رد شدن
4. در صورت نیاز: گرفتن `OrderId` واقعی از پاسخ و بررسی با `GetOpenOrder`

## ابزارها
- `pw/order2.js` — ورود + بایند + پر کردن + کلیک + ضبط شبکه (تک‌نشستی)
- `pw/probe.js` — بررسی ساختار پنل بدون ناوبری
- `pw/check_orders.js` — خواندن سفارشات باز از API
- لاگ بدنهٔ آخرین درخواست: `data/order_payload_log.txt`

## دور ۳ — فراخوانی مستقیم API

با fetch از داخل صفحهٔ واردشده، همان payload پنل فرستاده شد:
- با isin درست: `{"Data":{"OrderId":0},"IsSuccessfull":true}` — همان پاسخ پنل
- با isin خالی: `{"Data":null,"IsSuccessfull":false}` — یعنی اعتبارسنجی سرور کار می‌کند
- با پرچم‌های Caution/Sepah = true: خطای ۵۰۰ «خطا در انجام عملیات»
  → این نمادها به آن تاییدیه‌ها نیاز ندارند؛ مقدار درست همان false است

نتیجه‌گیری: payload درست است و سرور «موفق» می‌گوید، ولی `OrderId = 0`
یعنی سفارش در سامانهٔ معاملات نهایی نشده. علت هنوز پیدا نشده.

قدم بعدی:
1. یافتن endpoint تاریخچهٔ سفارش‌ها (GetTodayOrders / GetOrderHistory) برای دیدن
   اینکه کارگزار برای این سفارش چه وضعیتی ثبت کرده
2. پایش کانال SignalR `orderstatev6` (LsService.PrivateSubscribe) هنگام ارسال
3. مقایسه با یک سفارش موفق قدیمی (اگر در تاریخچه موجود باشد)

ابزار: `pw/api_order.js <symbol> <qty> <price> <isin>`

## دور ۴ — علت پیدا شد: «تاییدیهٔ معاملات تحت احتیاط»

پنل هنگام کار با سفارشات این دو درخواست را می‌زند:
```
GET /Web/V1/Agreement/GetActiveAgreementList
 → Data:[{AgreementId:2, AgreementText:"فرم پذيرش اطلاع از ابهام معاملات تحت احتیاط"}]

GET /Web/V1/Agreement/CheckAgreement
 → {"Data":0,"IsSuccessfull":false}      // یعنی تاییدیه پذیرفته نشده
```

پس علت خاموش بودن رد سفارش روشن است:
کارگزار تا وقتی این تاییدیه پذیرفته نشود، سفارش را ثبت نهایی نمی‌کند
(و پاسخ API را با OrderId=0 برمی‌گرداند، بدون پیام خطا).

### تلاش برای پذیرش از طریق API
نقطهٔ پایانی‌های موجود:
```
/Web/V1/Agreement/AcceptAgreement
/Web/V1/Agreement/ChangeAgreementState
/Web/V1/Agreement/GetAgreement
/Web/V1/Agreement/CheckAgreement
```
همهٔ حالت‌های آزمایش‌شده (AgreementId, Id, agreementId, body خالی, query, form) پاسخ دادند:
```
{"Data":false,"MessageDesc":"Sent id is not correct","IsSuccessfull":false}
```
یعنی نام/شکل پارامتر «id» متفاوت است.

### قدم بعدی
1. در پنل، تاییدیه را با کلیک روی مودال بپذیریم و **درخواست شبکه‌اش را ضبط کنیم**
   تا شکل دقیق پارامتر معلوم شود
2. سپس همان درخواست را در ربات تکرار کنیم
3. بعد از پذیرش، سفارش را با پرچم‌های Caution=true بفرستیم

## 🎉 دور ۴ (ادامه) — اولین سفارش خودکار موفق با Playwright

### شاهد
اجرای `pw/flow.js "آواپارس" IRO3AVPP0001 1000 6900`:
```
message : «سفارش خرید آواپارس1 با موفقیت در سیستم ثبت شد.»
open    : {"Data":[{"symbol":"آواپارس","nsccode":"IRO3AVPP0001","symbolid":0,...}]}
```

یعنی ربات، بدون هیچ کلیک انسانی:
1. با OCR وارد شد
2. نماد را با جستجوی دیده‌بان بایند کرد
3. آستانه حجم را خواند (۳۰۰٬۰۰۰)
4. تعداد و قیمت را پر کرد
5. روی خرید کلیک کرد
6. سفارش ثبت شد و در فهرست سفارشات باز ظاهر شد

### نکتهٔ مهم
- تاییدیهٔ Agreement همچنان `Data:0` است، ولی سفارش ثبت شد
  → پس این تاییدیه مانع سفارش نیست (فرضیهٔ دور قبل رد شد)
- نمادهای آباد و آردینه با همین مسیر **ثبت نشدند** (OrderId=0، بدون پیام)
  → علت، مخصوص همان نمادهاست (احتمالاً توقف/شرایط معاملاتی خاص)
  → دور بعد: خواندن «وضعیت نماد» از پنل قبل از سفارش و رد کردن نمادهای غیرمجاز

### فایل‌ها
- `pw/flow.js` — مسیر کامل سفارش (ورود، بایند، پر کردن، کلیک، بررسی نتیجه)
- `pw/login.js` — فقط ورود با OCR
- `pw/probe.js` — بررسی ساختار پنل

## دور ۵ — دو قاعدهٔ کلیدی کشف شد و سفارش‌ها ثبت شدند

### نتیجهٔ عملی
```
آواپارس  1,000 سهم @ 6,900   → ثبت شد
آردینه     200 سهم @ 45,070  → ثبت شد
آردینه   5,000 سهم @ 45,070  → ثبت شد
آردینه  10,000 سهم @ 45,070  → ثبت شد
آباد    20,000 سهم @ 1,809   → ثبت شد
آباد   100,000 سهم @ 1,809   → ثبت شد
```

### قاعدهٔ ۱ — قیمت باید از پنل باشد، نه از فایل
- آباد با قیمت ۱٬۹۱۹ (پایانی دیروز × ۱٫۰۳) **رد شد**
- همان نماد با قیمت ۱٬۸۰۹ (آخرین قیمت پنل) **ثبت شد**
→ محاسبهٔ سقف از فایل روزانه دیگر معتبر نیست؛ قیمت باید از خود پنل خوانده شود.

### قاعدهٔ ۲ — سایز باید با «موجودی آزاد» باشد، نه «قدرت خرید»
پاسخ `Accounting/Remain`:
```
RealBalance      : 3,319,229,960
BlockedBalance   : 2,965,972,938   ← سفارش‌های باز قبلی
AccountBalance   :   353,257,022   ← پول واقعاً آزاد
PurchasingPower  : 3,319,229,960
```
- آردینه با ارزش ۱٬۰۸ میلیارد **رد شد** (بیشتر از موجودی آزاد)
- همان نماد با ۲۲۵ و ۴۵۰ میلیون **ثبت شد**
→ سایز هر سفارش = min(موجودی آزاد, آستانه حجم)

### سفارشات باز (تأیید از API)
```
آردینه  : orderid 3026110720006778 · 200 سهم · status «ثبت در سیستم معاملات»
آواپارس : orderid ... · 1,000 سهم
```
